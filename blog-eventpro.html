Leading the EventPro Frontend: A Multi-Role Event Platform Built by a 9-Person Team

How I led the frontend of a three-role event platform: 100+ merged PRs, role-aware routing, real-time check-in and CSV validation — and what I would do differently.

T
Anthony Michael (TonyDev)
Frontend Developer · Nigeria 🇳🇬

The Problem That Started It All

Event management in Nigeria and honestly across much of Africa, is still largely manual. Organizers uses spreadsheet, WhatsApp groups to confirm attendees. Check-in is done with printed lists and pens. Duplicate registrations go undetected until someone shows up claiming a seat that was already taken.Long queues of attendees in hot weather. Attendance data lives in Excel files that get emailed around after the event, if at all.

EventPro was built by our TechCrush Bootcamp 2026 team to solve exactly these problems. The goal was a single platform where an admin could manage organizers, organizers could manage their events, and attendees could register for events seemlessly, get confirmed, and check in with ease without long standing, — all without a single WhatsApp message or printed list.

The core question: Can a bootcamp team ship a multi-role platform with a frontend built entirely in vanilla JavaScript, without it turning into spaghetti?

My role: Frontend Lead on a 9-person team. I led 100+ merged PRs across 19+ feature branches and built the frontend: role-aware routing, real-time check-in, CSV validation and the Appwrite auth integration. The backend and API were built by my teammates; this post covers the frontend side only.

Short answer: yes, with discipline. It took planning, strict conventions and a lot of code review. This is that story.

Deciding the Frontend Architecture Before Writing a Line

The first week was planning, not code. The three-role system — Admin, Organizer, and Attendee — shaped everything else. Each role needed:

  • Its own dashboard with different navigation, data, and permissions
  • A UI that never exposes another role's screens or actions
  • A shared auth flow that routes users to the right dashboard after login

We chose vanilla HTML, CSS and JavaScript for the frontend. With a team of 9 and a bootcamp deadline, the goal was to keep the barrier low for every contributor and to prove the fundamentals before reaching for a framework.

The file structure decision

With 20+ screens across three roles, the structure had to be planned or it would become a nightmare. We landed on this: 

EventPro-Frontend/
├── assets/images/           — logos, illustrations, icons
├── js/
│   ├── services/
│   │   └── auth-service.js  — login, logout, token storage, profile fetch
│   ├── utils/
│   │   └── load-components.js — role-aware sidebar + topbar injection
│   ├── admin-dashboard.js
│   ├── create-event.js
│   ├── csv-validation.js
│   ├── duplicate-detection.js
│   ├── organizer-dashboard.js
│   ├── real-time-attendance.js
│   └── ...one script per page
├── pages/                   — one HTML file per screen (20+)
├── styles/
│   ├── dashboard-layout.css — shared sidebar + topbar shell
│   └── ...one stylesheet per page
└── README.md

The key idea was auth-service.js — a single file that owns every API call the frontend makes. No page calls fetch() directly, so when the backend URL changed, the fix lived in one place.

Working Against the Backend Contract

My teammates built and documented the backend API with Swagger. As frontend lead, my job was to consume that contract cleanly: agree on the response shapes early, centralise every request in the service layer, and handle every failure state in the UI instead of letting a raw error reach the user.

Role-aware routing

All three roles share one login. After sign-in, the frontend reads the user's role and redirects to the matching dashboard, and each page checks the role on load so a user cannot browse into another role's screens. This is a UX guard only — real authorisation always has to be enforced by the server.

Security lesson: Frontend role checks improve the experience, they are not security. Never trust the client; the backend must validate permissions on every request.

Auth via Appwrite

SMS and email verification were integrated with Appwrite, a backend-as-a-service that handles OTP delivery. Using it was a deliberate choice: building OTP delivery from scratch means managing deliverability, SMS gateways and rate limiting. Good engineers know when not to reinvent the wheel.

The Features That Were Hard to Build

Real-time attendance tracking

Real-time means the dashboard updates live as attendees check in, with no page refresh. On the frontend this is done with polling rather than WebSockets: every 10 seconds the attendance screen silently fetches the latest check-in data and updates the UI if anything changed. It is less elegant than a persistent connection, but simpler to deploy and enough for events with tens to hundreds of attendees.

CSV upload with validation and duplicate detection

Bulk importing attendees sounds simple. It is not. The upload flow needed to:

  • Accept a CSV file with arbitrary column names
  • Map the columns to the expected fields (name, email, phone)
  • Detect and flag duplicates before anything is submitted
  • Give the organizer a clear error report for every invalid row
  • Let valid rows through without stopping for the invalid ones

The frontend shows a summary — for example "47 valid, 3 duplicates, 1 invalid email" — before anything is committed, so the organizer is never surprised.

The Frontend — 20+ Screens in Vanilla JS

Building 20+ screens without a component framework means solving shared UI manually. The sidebar appears on every dashboard screen. In React you would use a layout component; in vanilla JS we built load-components.js, a utility that fetches shared HTML fragments and injects them into a placeholder on each page.

The CSS architecture was equally deliberate. dashboard-layout.css defines the shared design tokens and components (cards, tables, badges, modals, toasts) and the responsive breakpoints. Each page imports it first and adds only page-specific styles, so a button looks identical on every dashboard because it is literally the same class.

The design system

The purple sidebar (#6F00FF) was chosen on purpose: purple signals premium and trust, and the white active state gives users a clear anchor for where they are.

Working as a 9-Person Team

Leading the frontend was as much about process as code. We used feature branches, pull requests and code review on every change, which is how the frontend reached 100+ merged PRs across 19+ branches without the main branch breaking. Small PRs, clear naming and fast reviews mattered more than any technical choice.

Deployment and What Broke

The frontend is deployed on GitHub Pages. The issue that cost me an afternoon: GitHub Pages is case-sensitive. Sign-In.html and sign-in.html are different files on Linux but identical on Windows, so every internal link had to be audited and corrected.

The API is hosted on a free tier that can sleep when idle, so the first request after a quiet period can be slow. That is why the auth service shows a friendly "The server may be starting up — please try again" message instead of a generic error.

Deployment trap: Lower-case every filename and every link before deploying to Linux-based hosting, or develop on a case-sensitive file system.

What I'd Do Differently

Honest retrospective — three things I would change:

1. Use a module bundler from day one. With 30+ JavaScript files and no bundler, load order and global scope pollution became a real problem. Vite would have added minimal overhead and solved it.

2. Agree the API contract before building screens. Mocking responses from an agreed contract lets frontend and backend move in parallel without blocking each other.

3. Plan the mobile layout before building desktop. The dashboards were designed desktop-first and mobile was retrofitted. It works, but some screens, like organizer management, are tighter than they should be. Mobile-first would have caught this.

What I'm Proud Of

EventPro is a real, deployed product built under real constraints: a team of 9, a bootcamp deadline and 20+ screens across three roles. I am proud of the frontend architecture, the review discipline that kept it stable, and of leading a team through it.

What's Next for EventPro

Planned next: payment integration for ticket sales, a better mobile organizer dashboard, and QR-code check-in so attendees can be scanned at the door. The frontend source is on GitHub — dig in and open an issue if you spot something broken.
